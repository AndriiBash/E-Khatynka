# Аналітичний модуль «Є-Хатинки»: модель, алгоритми, оцінка

Документ описує, що саме реалізовано в `src/server/analytics/*` і чому — щоб
його можна було використати в розділах дипломної роботи про формалізацію
процесів, вибір математичних моделей і комбіновану підсистему рекомендацій.

## 1. Концептуальна модель

Дані (без нових таблиць — усе рахується «на льоту» з наявної БД):

| Сутність | Звідки | Для чого |
|---|---|---|
| Продажі за днями/годинами | `orders` + `order_items` (без `cancelled`) | часові ряди попиту, профіль годин |
| Склад, термін придатності, ціна, знижка | `products` | залишки, знижки, швидкопсувність |
| Рецептури, залишки інгредієнтів | `product_recipes`, `ingredients` | потреба в інгредієнтах |
| Покупки користувача, вибране, теги | `orders`, `wishlists`, `user_tag_preferences` | рекомендації |

Потік: **історія замовлень → прогноз попиту (по товару, по днях) → план
виробництва (з урахуванням собівартості й терміну) → потреба в інгредієнтах**;
паралельно **швидкість продажів + залишок + термін → пропозиція знижки**;
**історія користувача + інші покупці → персональні підписи в каталозі**.

Модуль побудовано так, що цикл замкнений: застосована знижка змінює ціну в
каталозі, нові замовлення змінюють історію, наступний розрахунок це враховує.

## 2. Прогноз попиту (`models.js`, `forecast.js`)

Ряд — продані штуки товару за день (нулі зберігаються). Кандидати:

1. Сезонний наївний (значення тиждень тому) — **лише базова лінія для порівняння**.
2. Ковзне середнє за 28 днів.
3. Середнє за днем тижня зі зсувом до загального середнього (shrinkage, κ = 2).
4. Хольта–Вінтерса (адитивний, період 7, загасаючий тренд φ = 0,9; α, β, γ — перебір по сітці).
5. Ridge-регресія: тренд + 7 індикаторів дня тижня, L2-штраф на сезонні коефіцієнти.
6. Кростон-SBA — для переривчастого попиту (багато нульових днів).
7. Ансамбль: середнє (3) + (4) + (5).

**Вибір моделі — окремо для кожного товару** за rolling-origin backtest
(3 вікна по 7 днів; навчання лише на даних *до* вікна). Критерій — MAE; при різниці
до 3% перевага ансамблю (стабільніший). Наївний метод кандидатом не є.
Метрика звіту — **WAPE** = Σ|прогноз − факт| / Σ факт.

Сезонність: тижнева (день тижня) — у моделях; добова (година) — через профіль
годин замовлень (окремо для буднів/вихідних, глобально й по категорії).
Річну сезонність оцінити неможливо без ≥ 1 року історії — це чесно
вказано на вкладці «Моделі й точність».

«Довіра» (висока/середня/низька) залежить від довжини історії та WAPE товару.

## 3. План виробництва (`production.js`)

Модель «продавця газет» (newsvendor). Для товару зі ціною *p*, собівартістю
*c = costRatio·p* і часткою повернення з нерозпроданого *s* (залежить від терміну
придатності: 0 при ≤ 1 дні, 0,35 при 2 днях, 0,6 інакше):

    недобір = p − c,   надлишок = c − s·c,   CR = недобір / (недобір + надлишок)

Цільова кількість — квантиль порядку CR розподілу попиту (Пуассон при μ < 10,
нормальне наближення інакше). Від першого дня віднімається поточний залишок.
Кількість розбивається по частинах доби (ранок/день/вечір) за реальним
профілем годин методом найбільших залишків (сума цілих зберігається).

**Охоплення:** прогноз, план і аналіз знижок будуються для всіх товарів із БД, потреба — для всіх інгредієнтів складу (ті, що не входять до жодного рецепта, показуються зі статусом «Немає в рецептах»; залишок нижче `low_stock_threshold` теж позначається).

**Потреба в інгредієнтах** = Σ (кількість до випічки × норма з рецепта),
порівнюється із залишком: `critical` — не вистачає на завтра, `low` — на тиждень.

## 4. Знижки (`discounts.js`)

Аналізується весь асортимент. Ризик списання (`overstock`) рахується лише для швидкопсувних товарів (термін ≤ 7 днів); для решти (напої, фасовка) — лише сигнал «мало продажів». Ознаки: швидкість продажів
за 14 днів відносно медіани категорії, різке падіння за тиждень, залишок
відносно прогнозованого попиту до кінця терміну. Статуси: `overstock`
(залишок не розійдеться за строк), `slow`, `ok`.

Розмір знижки — найменший крок (5%), що знімає надлишок за припущеної
еластичності −1,5, з обмеженнями: не більше 40% і не нижче собівартості × 1,1.
Оцінка приросту попиту — **припущення**, а не виміряний факт (параметри в `config.js`).
Без достатньої історії товар не оголошується «повільним».

## 5. Гібридна рекомендаційна система (`recommender.js`)

Для користувача формуються два списки, що відображаються як підписи в
розділі «Усі товари» (лише авторизованим):

* **«Ви брали раніше»** — куплені товари, ранжовані з експоненційним
  згасанням (напівперіод 30 днів);
* **«Це беруть також інші»** — нові для користувача товари з гібридним рейтингом.

Гібрид = 0,6·CF + 0,2·CB + 0,2·Pop (кожен компонент min-max нормалізований
по списку кандидатів):

* **CF (item-based)**: косинусна подібність L2-нормованих векторів покупців товару;
  профіль користувача — зважена сума подібностей до його покупок;
* **CB (контентна)**: TF-IDF-вектор (категорія, теги, інгредієнти, ціновий сегмент);
  профіль — куплені/вибрані товари та улюблені теги (`user_tag_preferences`);
* **Pop**: загальна популярність; товар «немає в наявності» отримує штраф ×0,5.

Холодний старт: без покупок вирішують теги-вподобання, контент і популярність.

**Прямий збіг із тегами профілю.** Якщо покупець обрав улюблені теги, до
рейтингу додається окремий компонент `tagMatch` (частка його тегів, що є в
товару) з вагою `weightTag = 0,3`; решта складових стискається пропорційно
(`score = 0,7·(CF, CB, Pop) + 0,3·tagMatch`). Раніше теги діяли лише через
контентну складову (0,2) і тонули в профілі покупок. Товари без залишку у
рекомендації не потрапляють (в каталозі їх не показано). Компроміс: на
синтетичних даних при короткій історії (2–3 замовлення) Hit@5 зменшується на
~0–5 п.п. (67,2% проти 67,2% при M=3; 70,5% проти 75,4% при M=2), при 5
замовленнях — не гірше; це ціна за те, що явний вибір користувача перестає
ігноруватися. Вагу можна змінити в `config.js`.

## 6. Оцінка рекомендацій і чесні застереження

Реальних замовлень у БД замало (2 шт.), тому для демонстрації є
окремий одноразовий скрипт (у проєкт не входить) створював **синтетичну** історію (детермінований генератор,
90 днів, 60 покупців, тижнева сезонність, персональні смаки, ~8 навмисно
«повільних» товарів). Створює демо-акаунти (`demo1@ehatynka.demo` / `demo1234`),
демо-акаунти мали id `u_demo_*`.

**Всі числа нижче отримано на синтетичних даних, тому це перевірка
працездатності алгоритмів, а не доказ якості на реальних покупцях.** Дані
згенеровано моделлю, що містить ті самі припущення (сезонність, смаки), яку
потім «відкривають» алгоритми, — це завищує точність. У дипломі так і
треба писати; на реальних замовленнях числа треба перерахувати.

### 6.1. Прогноз (WAPE, 90 днів, rolling-origin)

| Модель | WAPE по товарах | Обрано для товарів |
|---|---|---|
| Сезонний наївний (t−7) | 78,3% | — (база) |
| Ковзне середнє 28 дн. | 60,6% | 7 |
| Середнє за днем тижня | 59,8% | 9 |
| Кростон-SBA | 60,4% | 9 |
| Хольта–Вінтерса | 61,5% | 3 |
| Ridge | 60,9% | 6 |
| Ансамбль | 60,1% | 21 |

Обрані моделі: 57,4% проти 78,3% у наївного. По окремому товару похибка велика,
бо продажі дрібні (кілька штук на день, переважно шум). **По загальному обсягу
WAPE ≈ 21,6% проти 23,9% у наївного** — виграш скромний, і це варто чесно
зазначити: на синтетичних даних тижнева сезонність слабка, а окремі моделі
відрізняються між собою мало (різниця в межах ~2 п.п.).

### 6.2. Рекомендації (одноразова офлайн-оцінка)

Протокол: відомі перші 3 замовлення покупця, мішень — нові товари з наступних 3
замовлень; 60 покупців. Ваги гібрида підбиралися по сітці на цих же даних
(ризик перепідгонки — підбір і оцінка не розділені).

| Метод | Hit@5 | P@5 | Hit@10 |
|---|---|---|---|
| Гібрид (CF+CB+Pop) | 66,7% | 21,3% | 85,0% |
| Лише CF | 71,7% | 25,7% | 90,0% |
| Лише CB | 53,3% | 13,7% | 85,0% |
| Лише популярність | 68,3% | 23,0% | 88,3% |

Висновок: за цим протоколом **гібрид не перевершив чистий CF**, а від
популярності майже не відрізняється; контентна складова окремо слабка.
Гібрид залишено заради стійкості до холодного старту (нові користувачі,
нові товари) та тому, що популярність на синтетичних даних штучно сильна
(генератор сам задає популярність категорій). Ці висновки треба перевірити на
реальних даних, перш ніж стверджувати перевагу гібрида.

## 7. Обмеження

* Собівартості в БД немає — взято частку від ціни (`costRatio`).
* Продажі обмежені залишком: реальний попит на дефіцитні позиції вищий за спостережуваний.
* Еластичність −1,5 — припущення; ефект знижок не виміряно.
* Мало користувачів → CF шумний; модель перебудовується при кожному запиті (без кешу).
* Модель не бачить погоди, свят, акцій конкурентів.
